## 0. 一句话结论

**go（可做），且比 `P13 §5` 设想的更轻。** 三句话：

1. **外部会话状态的唯一来源是客户端 hook 事件** —— 没有第二条路。外部参考实现同样**不读**会话文件 / transcript / 数据库，
   没有 hook 就没有任何状态（这也是它 README 里「没有显示会话」排查清单第一条就叫用户确认 Hook 是否接入的原因）。
2. **不需要独立进程、不需要新窗口、不需要周期轮询。** 本仓 P9 的窗口与数据契约**原样承载**外部会话行
   （`CompanionItem.source` 按设计就是「跨来源」字段，`companion.rs:5-8`）。
   ⇒ **本 spike 对 D39 的推荐与 `P13 §5` 相反**，理由见 §2 Q2。
3. **写客户端 hook 配置所需的基础设施本仓已经全有**（`client_settings.rs`：点号路径补丁 + 自动备份 +
   进程守卫 + 一键还原）。缺的只有「**数组追加式合并**」这一层语义（见 §3.2）。

## 2. 四问逐条判定

### Q1 · 窗口分叉：第二个悬浮窗，还是复用 P9 窗口？ ⇒ **复用 P9 窗口**

| 项 | 内容 |
|:---|:---|
| **statement** | 外部会话行可以直接落进本仓**现有** P9 悬浮窗，不需要第二个窗口 |
| **how** | 读 P9 的数据契约与窗口实现（只读） |
| **pass** | `CompanionItem` 的字段能无损表达一条外部会话 |
| **failCriterion** | 外部会话需要 P9 契约里**没有**的信息（如实时进度百分比、内联审批按钮）才有意义 |
| **verdict** | **pass** |
| **evidence** | ① `companion.rs:53-64` 的 `CompanionItem { id, source, title, state, hint }` —— **`source` 字段的文档就写着「来源客户端名」，`source` 枚举里已有 `live/unavailable` 两种 provider 态**；② `companion.rs:5-8` 模块文档：「悬浮窗展示的是**跨来源的**『会话 / 任务状态』……**不属于任何单一 scope**」⇒ **外部会话本来就是这个模型的题中之义**；③ `P13 §4.3` 自己写明「本仓 P9 的数据模型**已经预留了替换点**……**P15b 不需要改前端契约**」 |

**为什么不新开窗口**（反驳 `P13 §5` D39 的「新开一个窗口，不替换 P9 的窗口」）：

- 新开窗口的直接后果是**两个悬浮窗共存**：一个恒空（自家 `switch-progress` 只在切号那几秒有内容）、一个显示外部会话。
  这正是 `P9-ARCH §1.5` 那条纪律要防的形态 —— 该条原文针对的是「第二个看起来能切的控件」，
  而**两个各自有显隐入口的悬浮窗**是同一类问题的放大版。
- D39 给「新开窗口」的两条理由都不成立：① 「绕开 `BackgroundTask` 风险面」是**进程模型**问题，与窗口数量无关（见 Q2）；
  ② 「P9 已有键盘门禁，替换会丢门禁」——**复用窗口 ≠ 替换实现**。provider 换掉之后，
  键盘可达（`companion-app.tsx` 的 `focusEntry`）、标题不进 DOM（`companion-row.tsx`）、
  可见性三面收敛、Esc 隐藏**全部原样保留**，门禁第 227 条继续生效。
- ⚠️ **唯一需要新决策的点**：外部行进来后，窗口的**空态文案**要改 —— 现在的
  `shared.companion.empty.description`（「在客户端发起任务后，状态会显示在这里」）在只有自家数据源时是**不成立的**
  （见 §3.3）。这是文案问题，不是窗口分叉问题。

### Q2 · 进程模型：收集器放宿主内还是独立进程？ ⇒ **宿主内 + 纯事件驱动，零周期任务**（与 `P13 §5` D39 推荐相反）

| 项 | 内容 |
|:---|:---|
| **statement** | 收集器可以**完全事件驱动**：hook 到达时写状态，过期在**读取时惰性判定** ⇒ 无需任何周期性出口 |
| **how** | 读外部参考实现的轮询动机（其 `host_process` 模块）与本仓的后台任务约束 |
| **pass** | 「周期轮询」不是正确性所必需 |
| **failCriterion** | 存在**只有周期动作才能满足**的需求（如「客户端静默退出后必须主动把任务标为中止」） |
| **verdict** | **pass**（在 Windows 目标上；macOS/Linux 见「残留风险」） |
| **evidence** | ① 外部参考实现的周期轮询（1 s）**只服务一件事**：宿主客户端进程是否退出（其 `host_process` 模块）；② **该能力在 Windows 上被它自己禁用**（`supported = cfg!(macos \|\| linux)`，Windows 直接返回 `Unknown`）⇒ 对本仓的主力平台**不构成需求**；③ 「静默 45 min 转 unknown」「待确认 60 s 过期」在它那里是**读取时惰性计算**的（snapshot 阶段比较 `updatedAt`），**不是周期任务**；④ 本仓硬约束「登记即执行」（`background.rs:180` + `:281-296` 的两侧门禁）**不是禁止**新增任务，而是要求登记 —— 但**零任务比登记过的任务更省事**，且把「漏登记 ⇒ 永不执行」的事故面**归零** |

**为什么不用独立进程**（反驳 D39 的「独立进程承载收集器」）：

- 独立进程的**唯一剩余理由**是「把周期任务关在宿主外」。Q2 已经证明**不需要周期任务** ⇒ 该理由消失。
- 独立进程的代价是具体的：新增 externalBin 打包 / 分发 / 签名 / 更新链 / 进程生命周期管理 / 端口与所有权协商
  （外部参考实现为此写了 `interfaceVersion` 兼容边界，并引入**两条更新链** —— 这正是 `P13 §8.1` 明确不做的）。
- 本仓形态是**单进程桌面 App**（`src-tauri`），且**已有**本地 HTTP 服务设施（网关侧 axum 路由）。
  接收端挂在**同一个进程**里是最小改动。

**落点（P15b 用）**：新增一个**只绑 `127.0.0.1` 的监听**，端口按 `UNIFIED-GATEWAY-ARCH.md:115` 的登记表另选
（已占 57890 / 57891 / 7864 / 8899 / 57892）⇒ **另选并登记**（`P13 §4.3` 同条要求）；
校验基线照抄参考的六条（Host / Origin / 体积 / Content-Type / 方法白名单 / 不落盘正文）。

**残留风险（必须在 P15b 显式说明）**：不做宿主进程探测 ⇒ **客户端崩溃 / 强退后，未完成的任务会停在「运行中」**，
直到 45 min 静默阈值把它标成未知。这是**用户可感知的行为差异**，须在设置页文案里写明（「客户端退出后状态可能延迟收敛」）。
若日后要补，macOS/Linux 可加**一个已登记的**周期任务；Windows 维持不探测。

### Q3 · 隐私口径：外部会话标题要不要进 DOM？ ⇒ **沿用「不进 DOM」**

| 项 | 内容 |
|:---|:---|
| **statement** | 外部行的 `title` 默认**不写入 DOM**（渲染占位符），悬停 / `:focus-visible` 才展开 |
| **how** | 对比两侧的既有口径（只读） |
| **pass** | 不破坏 P9 既有红线即可 |
| **failCriterion** | 外部会话的可用性**必须**依赖标题常驻显示（如按标题搜索 / 无需交互即扫读） |
| **verdict** | **pass** |
| **evidence** | ① 本仓 P9 红线：`companion-row.tsx` 的 `COMPANION_TITLE_PLACEHOLDER`（`••••••••`）——
    文档理由整条就是**防截图泄露**，且明确「完整标题**根本不进 DOM**」；② 外部参考实现的 title 实测就是
    **prompt 前 240 字**（`slice(0, 240)`），**比本仓自家条目（「开始切换账号…」）敏感一个量级**；
    ③ 本仓 `CompanionRow` 已有完整的悬停 / 聚焦展开 + `aria-label` 脱敏描述实现 ⇒ **零新增成本** |

**代价**：「扫一眼就知道哪个任务在等我确认」这个体验**打折**（要先悬停）。
`P13 §5` D40 已把这条标为**产品决策**，本 spike 维持其推荐并补充量化依据：外部 title = prompt 前 240 字。

### Q4 · hook 安装面：要不要写用户其它客户端的配置？ ⇒ **要，基础设施工本仓已全有**

| 项 | 内容 |
|:---|:---|
| **statement** | 用本仓**现有**的客户端设置托管能力写 hook 配置，无需新造写入机制 |
| **how** | 读 `client_settings.rs` 的公开面 + 实测本机 `settings.json` 现状 |
| **pass** | 现有 `patch_settings` 能承载 hook 写入所需的**全部**护栏 |
| **failCriterion** | 写入需要「读-合并-写」语义而现有补丁只支持整值覆盖，且无法扩展 |
| **verdict** | **pass（带一处缺口）** |
| **evidence** | ① `client_settings.rs:351` `patch_settings(slot_key, patch)`，语义 = `{ "<点号路径>": <新值> }`，
    **格式保持**（缩进 / 换行指纹不解构）、**模块内部自动备份**；② `:356` **进程守卫已内建**：
    `if slot.is_running() { return Err(process_running(slot)) }`（对应 `error_code.rs:59` 的专用错误码）；
    ③ `:363` `list_backups` + `:369` `restore_backup`（**恢复前对当前文件再备份一次**）⇒ **一键还原**已有；
    ④ 本机两份 `settings.json` **都没有 `hooks` 键** ⇒ 无需处理历史遗留；
    ⑤ `CLIENT_SLOTS` 覆盖 WB 两区域，槽位路径由声明表驱动（`:137-146`） |

**缺口（P15b 必须补的一层）**：hook 的 `hooks.<Event>` 是**数组**，且用户可能已有**别人的** hook 条目。
`patch_settings` 是「整值覆盖」⇒ 直接用它写会把用户原有 hook **冲掉**。
需要一层 **hooks-aware 的合并**：读现有数组 → 剔除**自己的**旧条目（幂等）→ 追加自己的 handler → 写回。
外部参考实现正是这么做的（按命令串识别「是不是自己装的」+ 检测到新版就清理旧版）。
⚠️ **这一层必须与 `patch_settings` 共用同一套备份 / 进程守卫 / 格式保持**，不许另起一条写入路径。

**hook 命令的可执行从哪来（P15b 待验证，见 §4）**：客户端 hook 是**同步 command**（参考用 `timeout: 3`），
所以入口必须是**快速启动的 CLI**，不能是 Tauri 主程序（启动即拉起整个 GUI，太慢）。
本仓 `crates/buddy-switch-server` 已经是纯 CLI 且**已有子命令分发**（`main.rs:292`）⇒ 加 `hook` 子命令是低成本路径。
**但该二进制是否随桌面安装包分发，本 spike 未取证**（§4）。

## 3. 另外三处发现（其中两处**推翻既有文档**）

### 3.1 ★ 「WorkBuddy 无独立运行日志」的说法**是错的**

- 本仓 `src/locales/domains/shell.zh.ts:182-184` 写「本分区**暂无运行日志**……WorkBuddy 分区的运行日志在网关页可见」。
- **实测**：`~/.workbuddy/logs/` 存在，含 `automation.log` 与**按日期分的子目录**。
- ⇒ `history/reference-changexbc-workbuddy-switch.md` §5.4 标记的「本次调研里唯一一条会直接影响方案取舍的事实冲突」**已判定**：
  **外部参考实现的说法成立，本仓文案不成立**。
- **影响面**：① 走 hook 路线时，「沙箱审批不发 hook、靠日志补」这条**有落地前提**（不必先补一条"日志不存在"的结论）；
  ② 本仓设置页的日志分区文案**当前在误导用户**，应单独修（这属于既有 bug，与 P15 解耦）。

> ⚠️ 未取证：本机 `automation.log` 抽样只见调度器启动行，**未见审批行** —— 「日志里是否真有可解析的审批行」
> 需在 P15b 里用真实沙箱审批现场验证。§3.1 只判定「日志目录存在」这个**事实层**。

### 3.2 hook 写入是「合并」语义，不是「覆盖」

见 Q4 缺口。这条**改变了 P15b 的实现形状**：不能只是「调 `patch_settings` 写 `hooks.X = [...]`」。

### 3.3 悬浮窗空态文案与实现不符（既有缺陷，与 P15 解耦但同一处 UI）

- `shared.companion.empty.description` = 「在客户端发起任务后，状态会显示在这里。」
- **实际**：provider 只读自家 `SWITCH_RUNNING`（`commands.rs:3141` / `api.rs:3343` 两份同款），
  **完全不追踪客户端任务** ⇒ 该文案承诺了一件当时没实现的事。
- 附带：`P9-ARCH §1.3` 写的数据源是**三个**（`switch-progress` / `checkin-progress` / `trae-checkin-progress`），
  前端 `companion.ts:76-80` 也确实订阅了三个事件，**但 provider 只把 `switch` 映射成条目** ⇒
  **签到操作 100% 不产生条目**（前端刷新了也是空）—— 这是「实现比设计窄」，属于 P9 自身的未完成项。

## 5. go/no-go

**go。** 判据：

- 四问全部 pass（Q1 复用窗口、Q2 零周期任务、Q3 隐私无新增成本、Q4 基础设施已具备）。
- 唯一形态性变更：**不做独立进程、不新开窗口** —— 这与 `P13 §5` 的 D39 推荐相反，**须由 lead 明确拍板**（见 §6）。

**建议的实施切片**（每片可独立交付 / 独立回滚）：

| 片 | 内容 | 依赖 |
|:---|:---|:---|

## 7. 明确不做（沿用 `P13 §8`，本 spike 追加）

1. **不整体引入外部参考实现的组件树**（`P13 §8.1`）。
2. **不新增周期任务**（本 spike Q2 的结论）—— 若日后确实需要，**必须先登记两侧注册表**。
3. **不给 `CompanionState` 扩枚举** —— 外部实现的 6 态（`unknown/running/wait/done/error/aborted`）
   按 `P13 §4.3` 做**映射**：`wait → waiting`、`error/aborted → failed`、`unknown → 不渲染该行`（结构化空态）。
   ⚠️ 由此得一条**诚实边界**：**纯 hook 来源的会话几乎不会出现「失败」态**
   （hook 的 `Stop/SessionEnd/Interrupt` 只产生已完成 / 已中止），设置页文案不得暗示「失败」常用。
4. **不另起一条写客户端配置的路径** —— 必须走 `client_settings.rs`（§6 D41）。
