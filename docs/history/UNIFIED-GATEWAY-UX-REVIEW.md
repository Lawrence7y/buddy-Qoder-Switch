## 0. 一句话结论

「统一网关」乱，**不是样式问题，是位置问题 + 信息缺失**：

1. 它是**跨作用域**的，却被塞进三个**有作用域**的网关页里当第 7 项 —— 结构性错位，只能靠一行灰字打补丁。
2. 它是**唯一一个没有原型**的网关页（`demo-app.js` 里 grep 不到任何 unified 视图），所以交互质感与其余页面天然不一致。
3. 它**完全看不到账号池** —— 而路由恰恰是按池分派的。这是整页最该有、却没有的东西。

## 1. 现状诊断（7 条，逐条有出处）

### 1.1 【结构】跨作用域的页面被放进有作用域的页里

- `GATEWAY_SUBNAV` 共 7 项，`unified` 排最后（`src/components/gateway/gateway-subnav.tsx:40-48`）。
- 三个网关页**各渲染一次**同一个组件：
  - `src/pages/ApiServicePage.tsx:499`
  - `src/pages/TraeApiServicePage.tsx:657`
  - `src/pages/QoderApiServicePage.tsx:551`
- 每处页头都挂着**当前作用域的 `ScopeChip`**（`ApiServicePage.tsx:243`）。

**后果**：用户在 Trae 网关页点「统一网关」，看到的是同一份内容，页头却写着 Trae。唯一解释是卡 1 顶部一行灰字（词条 `unifiedGateway.crossScope`）—— **用文案给结构错位打补丁**。

### 1.2 【发现性】概览页没有「统一网关」入口行

设计文档 §1 明确要求：概览页加一行「统一网关」摘要 + 「查看」深链，与既有三行同构。
实际概览只有三行：上游凭据 / 可用模型 / 账号池（`ApiServicePage.tsx:435-475`）—— **没有统一网关**。

**后果**：用户只能靠自己注意到子导航最后那一项。

### 1.3 【结构】勾选与预览被拆到两张卡，中间隔着密钥表

- 卡 1 放「启用的命名空间」勾选（`unified-gateway-view.tsx:343-388`）
- 卡 2 是密钥表（`:391-510`）
- 卡 3 才是「命名空间与清单预览」（`:512-595`）

`UNIFIED-GATEWAY-UI.md:40-43` **自己论证过拆开是 bug**（"改一处要看两个地方"），落地时又拆开了，只在文档头部补了一句备注。

**后果**：勾掉一个命名空间，要滚过整张密钥表才能看到清单变化。

### 1.4 【可读性】命名空间以「代码」呈现，人话只藏在 title

```tsx
// unified-gateway-view.tsx:361-373
<code className="font-mono text-[11.5px]">{id}</code>
```

客户端名只进 `title={meta.client}` —— hover 才有人话，触屏 / 键盘用户拿不到。

**后果**：用户面对 `wb-cn` / `trae-global` / `traework-cn` / `traecode-cn` / `qoder-cn` 一串代码。
（注：`gateway-subnav.tsx:21-22` 记过一条「原型子导航没有图标」的教训 —— 同类问题：**把说明藏进 hover 等于没有说明**。）

### 1.5 【信息缺失】整页看不到账号池 ← 本次核心

`UnifiedGatewayView` 只有三张卡，**没有任何池相关数据**；后端 `unified` 模块的管理面只暴露三样：

```rust
// crates/buddy-switch-gateway/src/unified/mod.rs  admin 模块
keys_list_payload()   // 密钥
config_payload()      // 配置 + namespaces + keys 计数
models_preview()      // 清单预览
```

**但路由恰恰是按池分派的**：

```rust
// crates/buddy-switch-gateway/src/unified/routes.rs:222-275
RelayTarget::Wb(region)      => chat_for_region(wb, region, …)
RelayTarget::Trae(variant)   => chat_for_variant(trae, variant, …)
RelayTarget::Qoder(region)   => chat_for_region(qoder, region, …)
```

**每个命名空间背后就是一个池**（`gateway_namespace::relay_target_of`）。

**后果**：用户在「统一网关」启用了 `trae-cn`，却不知道 Trae 国内池里有没有可用账号、是否全在冷却。
要查必须切到 Trae 网关页 → 账号池，**而且一次只能看一个平台**。
「统一网关」作为唯一的跨平台视图，恰恰缺了唯一真正需要跨平台的信息。

### 1.6 【语义】状态不闭环 ——「已识别 ≠ 可用」

卡 3 只给 `source`（实时 / 已保存 / 内置）+ 条数（`unified-gateway-view.tsx:540-556`），**没有「现在能不能调通」**。

真正的可调用 = 命名空间已启用 ∧ 该命名空间对应的池有可用账号 ∧ 模型已识别 ∧ 模型未被禁用。
**前两项在页面上完全不可见。**

### 1.7 【联动】跨卡联动只做了一半

- 已做：卡 2 里授权了「已停用命名空间」的 Key 徽标标红（`:433-445`）。
- **未做**：设计文档 §4.1 要求「取消勾选时，勾选框旁出现 `warn` 徽标 + 受影响密钥数」，实现里只有 `title` 提示，**没有计数**。

## 2. 优化方案

分三档：**P0 结构 + 信息**（做完页面就站得住）、**P1 体验补完**、**P2 收尾**。

### P0-1 · 把「统一网关」搬出三个网关页，做成独立目的地

**理由**：它是跨作用域的，与三个有作用域的网关页本质不同。放一起必然要写「上方作用域选择器不生效」这种补丁文案。

**做法**：
- 导航加一项（侧栏全局区 / 顶栏），URL **不带 scope**（如 `/unified-gateway`，不走 `/s/{scope}/...`）。
- 三个网关页的子导航**删掉 `unified` 项**（`GATEWAY_SUBNAV` 回到 6 项）。
- 页头不再渲染会误导的 `ScopeChip`。

**收益**：补丁文案消失；概览页的「统一网关」入口行问题（§1.2）自然解决；同一个页面不再三处重复。

**风险**：动 `DESTINATIONS` / 路由 / 侧栏 —— 属于「结构变更」，需要一次确认。
**替代方案（低风险）**：先不做搬迁，只把 `unified` 提到子导航**第 1 项**，并在概览页补上入口行。结构错位仍在，但发现性与顺序问题先解决。

### P0-2 · 账号池进页面：每个命名空间一行「池健康」★ 本次重点

**后端**：加一条只读命令 `unified_gateway_pool_overview`，按命名空间聚合返回：

```jsonc
{ "namespaces": [
  { "namespace": "trae-cn", "target": { "product": "trae", "region": "cn" },
    "total": 3, "available": 1, "cooling": 2, "disabled": 0, "modelCooling": 0 }
] }
```

**实现上不新增逻辑**：复用三条产品线已有的池状态视图（前端 `poolOf(status, region)` 那一套数据），只是把「三个池」按命名空间投影出来。
⚠️ 注意 Qoder 的 `model_cooling` 是**按模型**报的、与账号级 `cooling` **正交**（`references/qoder-gateway.md` §2.1），不能合并成一格。

**前端**：
- 卡 1 摘要条加「可用账号 N / 共 M」。
- 卡 3 每个命名空间行加池徽标：`可用 N · 冷却 M · 禁用 K`，**点开深链**到该产品线网关页的 `?sub=pool`。
- 无可用账号时给可诊断文案（沿用既有的 `no_credential` 分档思路，别写死「异常」）。

**收益**：直接解决「不知道他的账号池」。这是唯一能把「统一网关」从**配置页**变成**运维页**的一步。

### P0-3 · 命名空间行给人话

`<code>` 后面**直接显示客户端名**（国内带 ` CN`），不再只进 `title`。
六名两两不同是既定规则（`MEMORY.md` 内核共用 ④），直接拿来用，不需要新数据。

### P1-1 · 勾选与预览合回一张卡

按 `UNIFIED-GATEWAY-UI.md` §2 的原意：一张「命名空间」卡，**上半勾选、下半逐段状态，行与勾选一一对应**；密钥表挪到它后面。

**收益**：改一处只看一个地方；「勾掉 → 该段变灰」在视线内。

### P1-2 · 「可用性」闭环

卡 3 每行加一个总判据徽标，四态：

| 徽标 | 判据 |
|:--|:--|
| 可调用 | 已启用 ∧ 池有可用账号 ∧ 有清单 |
| 无可用账号 | 已启用 ∧ 池可用数 = 0 |
| 未识别模型 | 已启用 ∧ 清单为空 |
| 已停用 | 未启用 |

**理由**：`UNIFIED-GATEWAY-UI.md` §4.2 自己就警告过「『已识别』≠『可用』，故不写『可用』」—— 那是对的，但正确做法是**给出真正的可用性判据**，而不是干脆不给。

### P1-3 · 补上跨卡联动的另一半

取消勾选时，在勾选框旁给 `warn` 徽标 + **受影响密钥数**（设计文档 §4.1 要求，当前未实现）。

### P2-1 · 区分两个网关

主网关卡（`ApiServicePage.tsx:300-390`，端口 **57891**）与统一网关卡（`unified-gateway-view.tsx:257-389`，端口 **57892**）都是「开关 + 监听地址 + 端口」，同一页里两张高度相似。

**建议**：卡 1 标题不要叫「统一网关」（与页面标题「API 服务」下的既有网关撞名），改为「统一网关网关」并加一句引导：

> 只用一个平台 ⇒ 用该平台自己的网关；一个 provider 用遍全部平台与版本 ⇒ 用统一网关。

### P2-2 · 补原型

在 `docs/prototype/demo-app.js` 加 `viewUnifiedGateway`，跑通既有门禁（`verify-demo.cjs` + 单文件门禁）。

**理由**：本仓纪律是「原型 1:1 同构」（账号页 / 网关页均有门禁 + CDP 验证）。统一网关是**唯一没走原型**的网关页 —— 这是它质感不一致的根因。不补原型，后续每次改都会继续分叉。

## 6. 第二轮方案与评估（2026-10-15）

> 本轮把「原型已改的」与「真实实现里实际长什么样」逐条对齐核了一遍。
> **结论：真实实现落后原型一大截，且有一个安全问题。**
> 下面 A 类是「必须补的偏差」，B 类是「原型也没有、需要你拍板的新缺口」。

### 6.1 A 类 · 真实实现与原型 / 设计文档的偏差（必修）

依据：`src/components/gateway/unified-gateway-view.tsx` 全文 + `UNIFIED-GATEWAY-UI.md` §3–§6 + 单文件原型。

| # | 偏差 | 证据 | 为什么必须补 |
|:--|:--|:--|:--|
| **A1** | ★★ **开放局域网「一键生效」，没有危险确认** | `unified-gateway-view.tsx:303-318` 的按钮 `onClick` 直接 `save({bind_addr:"0.0.0.0", allow_non_loopback:true})`；组件内**无 `riskOpen` / 无 `ShieldAlert` / 无 Dialog**。三个既有网关页都有：`ApiServicePage.tsx:99,150-162,504`、`TraeApiServicePage.tsx:133,260,662`、`QoderApiServicePage.tsx:108,205,556` | **这是安全问题**：同一件危险事（把网关暴露到局域网，局域网内任何设备都能消耗你的额度），别处要两步确认、这里一步。**违反「同一件事同一做法」硬约束**，设计文档 §6 也明确要求 `ShieldAlert` + `destructive` |
| **A2** | 卡序与归属偏离设计文档 §2 | 实现：卡1（含勾选）→ 卡2 密钥 → 卡3 命名空间预览。文档 §2 + 原型：卡1 → **卡2 命名空间（勾选与逐段状态**同卡**）** → 卡3 密钥 | 文档 §2 自己论证过「拆开是 bug：改一处要看两个地方」（`UNIFIED-GATEWAY-UI.md:40-43`）。实现把勾选留在卡1、预览推到卡3，中间夹密钥表 |
| **A3** | 无**接入指引** | 组件内 grep `IntegrationGuide` / `baseUrl` 零命中 | 既有三个网关页都有 `IntegrationGuide`。统一网关的卖点就是「一个 provider 用遍全部平台」，**接入方式反而不在页面上** |
| **A4** | 无**复制 Base URL** | `copyText` 只用在一次性明文对话框（`:626`）；摘要条是纯 `<span>`（`:271-279`） | 原型有复制按钮。用户现在要手抄 `127.0.0.1:57892` |
| **A5** | 无「裸模型名」说明行 + **5 条错误响应抽屉** | 组件内无对应实现 | 统一网关最容易踩的坑就是「忘了加前缀」。设计文档 §3.1/§3.3 明确要求，原型已实现 |

## 8. 第四轮定案：网关页内分「两个类型」（**取代 §7.1 的独立目的地**）

> 2026-10-15。**用户否决了 §7.1 的「侧栏独立目的地」**（原话：拆出来感觉更乱了），
> 改为**网关页内分两个类型**。已落地原型并验证（23 断言 / 6 变异全红）。

### 8.1 定案的形态

```
侧栏（6 项，不变）      网关页
  概览                  ┌ 左栏 ────────────┐  ┌ 主区 ──────────┐
  账号                  │ 网关类型          │  │                │
  用量                  │ [独立网关][统一网关] │  │   该类型的分区   │
  会话                  │ ─────────────── │  │                │
  网关  ←                │ 概览 / 密钥 / …   │  │                │
  设置                  └──────────────────┘  └────────────────┘
```

| 类型 | 分区 | 页头 | 说明 |
|:--|:--|:--|:--|
| **独立网关** | 概览 / 密钥 / 模型 / 账号池 / 请求代理 / 请求日志 | 当前作用域的 `scope-chip` | **跟着顶栏作用域走**（WB 57891 / Trae 7864 / Qoder 7865） |
| **统一网关** | 概览 / 命名空间 / 密钥 / 接入指引 | **「跨全部作用域」徽标**（不挂 chip） | **跨全部作用域**（57892） |

- 分区 id 前缀 `u-`，与独立网关的 6 个**不相交** ⇒ 一个 `gwSub` state 就够；切类型时**重置到该类型第一项**，且渲染时按当前类型 **fail-closed**（`gwSubId()`）。
- URL：`?dest=gateway&type=unified`；**两代旧深链都兼容**（`?dest=gateway&gw=unified` 与 `?dest=unified`）。

### 8.2 为什么这个形态更合理（评估）

**它比前两种都好，因为「类型」和「作用域」是两个正交的轴，而它把两个轴各归其位。**

| 方案 | 问题 |
|:--|:--|
| ① 子导航第 7 项 | 跨作用域的分区与 6 个**随作用域过滤**的分区挤在**同一层** ⇒ 必须写一行「上方作用域选择器对它不生效」去解释错位，页头还挂着会误导的 chip |
| ② 侧栏独立目的地 | **侧栏变乱**（用户原判）；而且「它仍然是网关」这件事被拆散了 —— 用户想找网关时要先猜是哪个入口 |
| ③ **类型（定案）** | 类型回答「**哪个网关**」，子导航回答「**这个网关的哪个分区**」；两个类型**共用同一套交互**；侧栏保持 6 项 |

**代价（必须承认）**：多一层 = **多一次点击**。缓解：默认类型 = 独立网关（绝大多数用户只用一个平台）；类型切换器常驻左栏顶部、一眼可见；子导航按类型重置，不会停在另一个类型的分区上。

**唯一的坑（已处理）**：作用域 chip 必须**按类型分家** —— 独立网关挂 chip、统一网关挂「跨全部作用域」徽标。不这么做，「内容与作用域无关却挂着作用域 chip」这个谎言会原样回来。

### 8.3 落地时踩到的一个真坑（值得记）

第一版把「网关类型」的分段控件也叫 `.seg` —— 而 `.seg` 是**全应用通用**的分段控件（用量页 tabs / 接入方式选择器 / 会话筛选都在用）。
在原型里再定义一次 `.seg` 会**全局改掉它们**（改成 `display:grid` 后那几个控件全变形）。

⇒ 改名为 `.gw-type-seg`，并加了一条**源码级守卫**：顶层 `.seg` 规则数必须恒为 4（原有条数），`.gw-type-seg` 必须为 4。**不许再犯。**

## 10. 统一网关的「账号池」——**它没有自己的池**

> 2026-10-15。用户提问：*「账号池哪些呢？」*（独立网关有「账号池」分区，统一网关当时没有）。
> 已补上分区并验证（**32 断言 / 7 变异全红**）。

### 10.1 事实：统一网关没有账号池

**统一网关是路由层，不是池的所有者。** 它按模型名的命名空间前缀，把请求分派到三条产品线各自的池
（`gateway_namespace::relay_target_of`）：

| 命名空间前缀 | 目标池 |
|:--|:--|
| `wb-cn` / `wb-global` | WorkBuddy 的两个池 |
| `trae-cn` / `trae-global` | Trae 的两个池（**合并版**） |
| `traework-cn` / `traework-global` / `traecode-cn` / `traecode-global` | **复用 Trae 的两个池**（扩展程序线） |
| `qoder-cn` / `qoder-global` | Qoder 的两个池 |

⇒ 统一网关**没有**独立网关那种「管理当前这一个池」的分区（指定账号 / 恢复 / 粘性都是**按产品线**设的）。
它该有的是**跨平台的只读汇总** —— 这正是它唯一的价值：一次看全。

### 10.2 补的分区

`GW_SECTIONS.unified` → 概览 / 命名空间 / 密钥 / **账号池**（与独立网关**同名同位**）。

- 骨架与独立网关的账号池分区**同形**：`cat-bar` 工具条 + **裸表** + 说明段；
- 表**按池分组**（`tr.uni-grp`，与命名空间表的平台分组同一套），组头给「池名 · 命名空间 · N 可用 · 共 M · **去该平台管理**」；
- 账号行只给 **账号 / 积分 / 状态**（**不给「选号」** —— 那是按产品线设的，这里改不了，摆一个改不动的控件是假的）；
- **空池组**给可诊断文案 + 「去该平台管理」出口（`trae-global` 就是这一档）；
- 计数**逐条从 `GATEWAY[target].pool` 数出来**，不另写一套；
- 按池**去重**（`traework-cn` / `traecode-cn` 与 `trae-cn` 同池，只列一次，组头里列出共用的命名空间）。

概览的「账号池」行深链改到这一区（此前指向「命名空间」分区）。

### 10.3 与「命名空间」表的「看池」的关系（两处都要，不是重复）

| 入口 | 回答的问题 |
|:--|:--|
| 命名空间表的「**看池**」（就地展开） | 「**这一段**背后是哪个池、几个可用」—— 不离开表，保持跨平台视野 |
| 「**账号池**」分区 | 「**所有**池一共什么样」—— 全量账号明细 + 去各平台管理的入口 |

### 10.4 一个需要记的语义差异

**两个类型有一个同名的分区「账号池」，但语义不同**：

| | 独立网关 · 账号池 | 统一网关 · 账号池 |
|:--|:--|:--|
| 范围 | **当前作用域的**那一个池 | **全部已启用命名空间背后的**池（跨平台） |
| 可写 | ✅ 指定账号 / 解除禁用 | ❌ **只读**（选号按产品线设，要去各平台页） |

⇒ 同名同位是**刻意的**（用户找「账号池」就该在同一位置找到），但**只读性必须在页面上说清楚**
（工具条右侧写了「只读汇总 —— 选号 / 粘性 / 恢复在各自平台的网关页」，每组也有「去该平台管理」）。

### 10.5 验证

```bash
NODE_PATH=<managed node workspace>/node_modules node docs/prototype/verify-unified-pool.cjs
# 32 passed / 0 failed
```

新增断言：账号池分区骨架（cat-bar + 裸表 + 说明段）/ **分组 = 去重后的池**（阳性对照 6）/
**账号行数 = 各池 pool 长度之和**（逐条数出来）/ 空池组有文案 + 出口 / 概览的「账号池」行深链到本分区。
变异 7 个仍全部打红。

### 10.6 顺带修掉的深链漏洞

`bootFromUrl` 原先只认**独立网关**的分区 id：`?type=unified&gw=u-pool` 会被前面的
`wantsUnified` 分支先写成 `u-ov`，**深链静默失效**（落到概览）。
⇒ 补一段：`gw` 若命中**统一网关**的分区 id（前缀 `u-`），类型自动跟上。
新增断言钉住（`?type=unified&gw=u-pool` ⇒ 真的落在 `u-pool`）。
**验证 33 passed / 0 failed。**

### 11.3 过程教训（值得记）

1. **多 agent 并行的前提是「配额 + 文件集不相交」**。本轮先按文件集切了三路（后端 / 10 组件 / 概览），
